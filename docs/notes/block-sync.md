# Block sync: extension loading and the block id negotiation

## A block id from the network is not necessarily a durable block id

`GetBlockIds`/`BlockIds` carry whatever the peer currently calls its tip, and for a node that is mining microblocks that is a *liquid* block id: the key block plus the microblocks applied so far. Every further microblock changes it, and none of the intermediate values is the id the block is finally persisted under. A node therefore stops resolving an id it advertised seconds earlier, without having rolled anything back and without being on a fork. `History.blockIdsAfter` resolves candidates through `heightOf`, which knows persisted ids and the current liquid id only, and returns `Seq.empty` when it recognises none of them.

This is why the requester must never send a *single* recently-received id as its only anchor. A normal request (`ApplierState.Idle`) sends `lastBlockIds()`, tens of persisted ids ending at genesis, so something in it always resolves. The optimistic request (`ApplierState.Applying(None, ext)`, issued while the previous extension is still being applied) used to send only `ext.blocks.map(_.id()).reverse`, frequently one id, always the newest and therefore the most perishable. It now sends those ids *followed by* `lastBlockIds()`: the extension's own ids first so a peer that still holds them answers with the shortest useful extension, local history after them so the request cannot come back empty.

The failure this caused was not subtle, and it is worth knowing the shape because it looks like a consensus bug. In `WideStateGenerationSuite` on CI, all three non-mining nodes repeatedly blacklisted the miner with `Peer did not return any signatures and is likely on a fork` and `GenericError("Fork contains no common parent")`, 60 events in one run, every single one following an optimistic request and none following a normal one. There was no fork: the peers' chains were a strict prefix of the miner's, identical block ids at every shared height. Each blacklist closed the connection, which dropped the miner below its configured mining quorum (`Quorum not available (0/3)`), so block production stalled, the peers fell further behind, transactions stopped reaching the miner, and its UTX pool sat empty at 0 while the peers held thousands.

The timing is the part that makes it deterministic under load rather than a rare race. The optimistic request is not sent when the extension arrives; `syncNext` holds while the applier state is `Applying(Some(buffer), _)` (`Holding on requesting next sigs`, logged 231 times on one node in one run) and only fires when the buffer drains. Measured gap between an extension being buffered and the request that reuses its ids: median 8 to 15 seconds, maximum 136. Against a liquid id that stays resolvable for one microblock interval, 1 second in that suite. The anchor is stale by one to two orders of magnitude whenever the node is actually behind, which is exactly when it needs to sync.

Tolerating the empty reply instead was considered and rejected. Once the request carries `lastBlockIds()` an empty answer means the peer resolves none of our *persisted* ids down to the finalized height, which is the fork condition the blacklist rule exists to catch, so the existing `onNewSignatures` behaviour is correct as it stands and weakening it would remove a real defence for a case that anchoring already prevents.

`WideStateGenerationSuite` goes from a 15m40s timeout to passing in 2m57s with all four nodes converged, and the empty-reply blacklist disappears entirely. `Fork contains no common parent` drops from 54 to 6 and still happens occasionally: an optimistic request is still asking about blocks the requester has not applied yet, so the extension it gets back can still reference a parent it does not hold. That path is inherent to optimistic loading and is a separate question from the blacklisting.

## `GetBlockIds` is capped at 200 ids, and the sender is not the one who notices

`BlockIdSeqSpec.MaxIds` is 200, `deserializeData` enforces it, and `LegacyFrameCodec.decode` responds to an oversize frame by calling `peerDatabase.blacklistAndClose` - so the *receiver* blacklists the *sender*, who sees only a closed connection. Concatenating the two anchor sources overruns this without care: `lastBlockIds(maxRollback)` is `height to max(finalized, height - maxRollback) by -1`, i.e. `maxRollback + 1` = 101 ids whenever finalization lags, and an extension is up to `maxRollback` = 100 blocks (`blockIdsAfter` answers with 101 ids and `onNewSignatures` strips the one already known). 201 ids, 6637 bytes against a 6604 limit, reachable precisely when a lagging node with stalled finalization is catching up. A peer can also drive it deliberately by answering with a long id list and delivering the matching blocks.

The request therefore takes only as many extension ids as fit beside the history, never the other way round: the history ids are the ones that guarantee a non-empty reply, so they must never be the ones truncated. `serializeData` also `require`s the cap, so an over-long list fails locally and loudly instead of getting the node blacklisted by its peers.

## A drop invalidates the optimistic load wherever it is, not only in the buffer

The discard-on-drop rule first covered only an optimistic extension that was already buffered when the one beneath it finished. The drop can just as well land while the optimistic blocks are still on the wire, and then nothing is buffered: the applier goes idle, the blocks arrive, and `extensionLoadingFinished` hands them straight to the applier as if they were a fresh, normally anchored extension. `onExtensionApplied` now treats any outcome other than `Appended` the same way in both cases: it abandons whatever is loading and restarts from `lastBlockIds()`. This is safe without tracking which request was optimistic, because while the applier is `Applying(None, ext)` every request `syncNext` can have issued is anchored on `ext`. Blocks from the abandoned request that arrive late fall through to the broadcast path, where a block that is not a child of the tip is declined without a blacklist.

The drop itself comes from liquid ids again. In `WideStateGenerationSuite` (run 37298213607) node10 fetched block `e62c5450`, which is the miner's block in an earlier liquid state. The miner then served `[5c903809]`: the same key block (same timestamp and reference) plus one more microblock. `ExtensionAppender` drops it on an equal score. The optimistic request sent while it was applying led with `5c903809`, the peer resolved it (it is the peer's own block), and replied with blocks built on it. node10 never held `5c903809`: the `MicroBlockInv` that would have taken it there arrived 69 s before `e62c5450` became node10's tip, and `nextInvs` evicts after `inv-cache-timeout` (45 s). Leading the request with more history would not have helped, because `blockIdsAfter` stops at the first id it recognises.

The single blacklist cost the run: it cut node10 off from the miner for 30 s, the 669 transactions node10 accepted over REST in that window reached only the other followers, and node10 never rebroadcasts. The followers' p2p validation queues were about 11 minutes deep, because `processBlock` and `processMicroBlock` hold the `BlockchainUpdaterImpl` write lock (fair) for the whole apply, every state read in UTX validation takes the read lock, and a follower behind under this load is applying blocks 65% of the time: node01 validated 4.8 tx/s against about 23 tx/s arriving. The suite sets `rest-api.minimum-peers = 1` so a node with no peers at all refuses broadcasts it could never relay. Do not raise it to the full peer count: the check in `TransactionPublisher` gates every transaction, relayed ones included, so the miner, left one peer short by the same blacklist, would refuse everything the followers relay to it.

## Sync timeouts start when the request is sent, not when it is queued

`RxExtensionLoader` writes `GetBlockIds` and `GetBlock` from its own thread, so netty queues each write as a task on the channel's event loop, behind every transaction broadcast already queued for that peer. In `WideStateGenerationSuite` (run 37437069789) that queue was 8 to 13 seconds deep: node10 decided to request blocks at 08:41:30.736, `TrafficLogger` saw the `GetBlock` go out at 08:41:38.808, and a transaction broadcast at 08:41:25.361 was written at 08:41:38.587. The 10 s `synchronization-timeout` used to start at the decision, so most of it was spent in our own queue, and the peer was blacklisted for latency that was ours. Both request timers now start from the write future (for a `GetBlock` batch, the last write's, since writes on one channel complete in order). Timers restarted on progress (`onBlock`, `onSnapshot`) are unaffected: nothing is queued there.

The same run shows why such a queue builds up, and it is not message volume (about 120 reads and 20 writes a second on that event loop). JFR over the 8 s window: at least 2.3 s parked on logback's console appender lock and 0.4 s in `System.out.write`, because `TrafficLogger` logged every transaction at TRACE on the event loop (see "Traffic logger" in `docs/notes/testing.md`), plus 3.4 s of GC pauses on a box at 100% CPU. Fixing the timer does not shorten the queue; the responder still answers late, and a liquid id it advertised can expire in the meantime, which the next section handles.

## A block the responder no longer has is answered, not ignored

`BlockIds` ends at the responder's current tip, which on a miner is a liquid id, and the requester asks for those blocks seconds later. If a microblock or a key block has superseded the id by then, `loadBlockBytes` cannot find it. `HistoryReplier` used to log `Error loading block` and send nothing, and the requester blacklisted the peer when its timeout ran out: in run 37437069789 node01 blacklisted node09 this way over `ef0a88f2`, a liquid id node09 had advertised 3 seconds earlier, and node10 did the same over `89d63989`.

It now answers with `BlockNotFound(id)`. On the wire that is the block message code (29) with the bare 32-byte id as payload. No valid block is that short, since the signature alone is 64 bytes (`BasicMessagesRepoSpec` pins it), so `MessageCodec.decode` tells the two apart by length before `PBBlockSpec` sees the bytes. The split lives in the codec rather than in a widened `PBBlockSpec` type because a union content type would turn the spec's `ClassTag` into `Object` and break `specsByClasses`. Nodes without this change parse the 32 bytes as a block, fail, and blacklist the sender; compatibility was deliberately not kept.

`RxExtensionLoader` keeps only the requested ids before the missing one: blocks after it cannot attach to anything we hold. If nothing precedes it, it asks for block ids again without blacklisting. Otherwise it applies that prefix once the prefix is complete, waiting for blocks still in flight if necessary. The prefix is marked `truncated`, so the score-mismatch check in `onExtensionApplied` does not compare it against the peer's declared score, which it cannot reach. A `BlockNotFound` that matches no pending request is ignored.

Microblock and snapshot requests (`MicroBlockRequest`, `GetSnapshot`, `MicroSnapshotRequest`) still go unanswered on a miss.
